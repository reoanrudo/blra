# 法令リーダー全文一括表示・画面簡素化設計

- 日付: 2026-08-02
- 対象: `web/`（hourei-rag 起点の Next.js 14 + Prisma 法令リーダー）
- 状態: 対話承認済み、文書レビュー待ち
- 正本DB: `hourei_rag`（PostgreSQL + Prisma）
- 関連: `docs/design-spec.md` v1.2 §19、`docs/HANDOFF.md`

## 1. 目的

第1段階のBLRAを「法令を速く読み、関連規定へ漏れなく移動できる法令リーダー」に絞る。最初の実装単位では、e-Gov法令検索の全文表示方式を参考に、現在の章単位・10条ずつの段階読込を廃止し、選択した1法令の全文を一括取得・一括描画する。

同時に、本文閲覧を妨げる常設の右パネル、適用時点バー、保存・注釈・閲覧履歴・確認項目の利用者向け入口を画面から外す。既存DB、取込処理、関連APIはこの実装単位では削除しない。

## 2. 調査結果と採用理由

2026-08-02にe-Gov法令検索とBLRA現行画面を同じブラウザ環境で計測した。

| 項目 | e-Gov 建築基準法 | BLRA 現行画面 |
|---|---:|---:|
| 本文取得 | 法令全文を1回で取得 | 対象周辺11条、以後10条ずつ取得 |
| 本文データ | 約2.48MB decoded / 約193KB gzip | 初期表示約1.4万文字 |
| 初期DOM要素 | 約15,183 | 約1,253 |
| 本文スクロール高 | 約116,268px | 約7,679px（初期ウィンドウ） |
| 遠方条文への移動 | 追加通信なし | 未取得範囲は複数回の追加通信が必要 |

e-Govは労働安全衛生規則でも約43万文字・約56,585 DOM要素を一つのスクロール領域へ描画していた。BLRA収録法令の最大本文量は約43万文字であり、同じ方式を適用できる範囲にある。

BLRAでは本文以外にも案件、用語集、おすすめ、実務論点、注釈、ハイライト等の取得が初期表示時に走る。読者フェーズではこれらの通信を止め、本文と目次を優先する。

## 3. 確定した設計判断

| 判断項目 | 決定 |
|---|---|
| 読込単位 | 現在開いている1法令の現行収録版全文 |
| 描画方式 | 全条文を一つのDOM・一つの主スクロールへ描画 |
| データ正本 | `hourei_rag` DB。e-GovのHTMLは利用しない |
| 表示規則 | BLRA既存の階層、条番号、見出し、字下げ、附則・別表、DB保存済みリンクの描画規則を維持 |
| 同一法令内移動 | 固定アンカーへ即時スクロール。追加通信なし |
| 検索・参照先 | 新しいブラウザタブで対象アンカーを開く |
| レイアウト | 左パネル + 本文の2列。常設右パネルは廃止 |
| 旧機能 | DB/APIは残すが、読者画面の入口と初期通信を外す |
| 適用時点 | バーを外す。旧 `anchor` / `asOf` UIは使用しない |

## 4. 対象範囲

### 4.1 実装するもの

1. 1法令全文の軽量データを返すAPI
2. 全文一括表示ビューア
3. 全条・項・号の固定アンカー
4. 目次から遠方条文への通信なし移動
5. 直接URLで開いた条文への初期位置合わせ
6. 2列レイアウトへの簡素化
7. 左パネルの「目次」「検索」への限定
8. 検索結果を新しいタブで開く動作
9. 不要な利用者データ通信の停止
10. 失敗時に本文を失わない部分失敗表示

### 4.2 この実装単位に含めないもの

- DB・Prismaモデル・既存APIの物理削除
- 論点索引の新データモデルと内部管理画面
- 用語定義リンクの新規抽出
- 条文末尾の「関連を表示」
- 日付を含まない恒久URLへの全面移行
- 削除条文の墓標ページ
- 旧版・将来版の保存
- 案件、Evidence、注釈、個人保存、AI

これらは全文ビューアが安定した後の独立した実装単位とする。

## 5. アーキテクチャ

### 5.1 データフロー

```text
/articles/{articleId}
  │
  ├─ Server: articleId から現行 Law / LawRevision / 表示メタデータを解決
  │
  └─ Client: /api/law-revisions/{lawRevisionId}/document を1回取得
       │
       ├─ document metadata
       ├─ compact toc
       └─ ordered article nodes
             │
             └─ FullLawViewer
                  ├─ BLRA既存描画規則
                  ├─ 全文DOM
                  └─ 固定アンカーへの位置合わせ
```

全文APIは版をキーにする。1回の応答で目次と本文の両方を返し、現行の `/api/law-toc` と `/api/articles/chapter-window` を読者画面から呼ばない。

### 5.2 全文API

新規エンドポイント:

```text
GET /api/law-revisions/{lawRevisionId}/document
```

応答の概形:

```typescript
interface FullLawDocument {
  law: {
    id: string;
    egovLawId: string;
    name: string;
    shortName: string | null;
  };
  revision: {
    id: string;
    editionKey: string;
    sourceDate: string | null;
  };
  toc: FullLawTocNode[];
  nodes: FullLawNode[];
  linksBySource: Record<string, FullLawLink[]>;
}
```

`FullLawNode` は既存描画に必要な情報だけを返す。最低限、`id`、`parentId`、`stableNodeKey`、`level`、`sortOrder`、条・項番号、`caption`、`title`、`text`、描画に必要な既存属性を含める。案件、注釈、閲覧履歴、レコメンド等の利用者データは含めない。

`linksBySource` には同じ現行法令集に収録された、DB保存済みかつ `isResolved = true` のリンクだけを含める。閲覧時の正規表現検出や推定リンク生成は行わない。

DB取得は選択した `lawRevisionId` と現行法令集の収録範囲で限定し、`deletedAt IS NULL` を強制する。再帰CTEで文書順のpathを作り、DB側で正しい順序へ並べて返す。

応答には `ETag` を付け、`Cache-Control: public, max-age=300, stale-while-revalidate=86400` を使用する。本番配信ではgzipまたはBrotli圧縮を必須とする。版の公開内容を修正した場合もETagが変わり、誤った長期immutableキャッシュを残さない。

### 5.3 全文ビューア

`ChapterScrollViewer` の代わりに `FullLawViewer` を追加する。既存の法令描画規則を再利用するが、利用者データを読むContextやArticleごとの副作用を持たせない。

全ノードを一つの文書ツリーとして復元し、条文ルート単位で描画する。本文のDOM IDにはURL安全な固定アンカーを使用し、内部にはDBのArticle IDと `stableNodeKey` の両方を保持する。

初期描画後、URLの対象Article IDに対応する要素へ `scrollIntoView` で位置合わせする。位置合わせ完了前に下端監視やURL同期を開始しない。全文描画後は追加取得を一切行わない。

IntersectionObserverで現在条を追跡し、左目次の選択状態を更新する。同一法令内の目次移動ではNext.jsの画面遷移を発生させず、スクロールと `history.replaceState` だけを行う。

### 5.4 DB表示規則の維持

全文方式は読込単位だけを変更する。次の既存実装を正本として再利用または純粋化する。

- `web/src/lib/article/article-renderer.tsx`
- `web/src/lib/article/legal-number-format.ts`
- `web/src/lib/link/link-renderer.tsx`
- `web/src/components/article/ChapterArticleBlock.tsx`

e-GovのHTMLやCSSをコピーしない。DBに保存された階層・順序・本文と、BLRAの描画関数から画面を生成する。

この実装単位はリンクの検証状態を新設しない。全文化によって新しい機械推定リンクを増やさず、現在DBに保存されている解決済みリンクの表示互換だけを保つ。`detectRuntimeLinks` による閲覧時の候補追加は全文ビューアでは実行しない。人手確認済みだけを公開する最終形は、Reference Edgeの確認状態と内部確認画面を追加する後続実装で完成させる。

## 6. 画面構成

### 6.1 レイアウト

デスクトップは左パネルと本文の2列とする。狭い画面は本文を基本とし、「目次・検索」ボタンで左パネルをドロワー表示する。

次を削除する。

- 右実務パネルと開閉ボタン
- 適用時点バー
- 左パネル下部の常設用語集
- 「検索・実務」という名称
- 閲覧履歴・確認項目タブ
- インライン注釈編集の入口

### 6.2 左パネル

左パネルは「目次」「検索」の2タブだけを持つ。

- 目次は全文APIの `toc` を利用する
- 検索は収録120法令を横断する既存検索を入口として維持する
- 検索結果は `<a target="_blank" rel="noopener noreferrer">` で新しいタブへ開く
- 論点索引は確認済みデータモデル完成まで「整備中」とし、既存の未確認トピックを公開しない

## 7. 不要通信の停止

読者画面の初期表示では、本文・目次・検索に不要な次の取得を行わない。

- `/api/projects/active`
- `/api/glossary`
- `/api/recommendations`
- `/api/notes`
- `/api/user-highlights/batch`
- 未確認の `/api/topics`
- `/api/articles/chapter-window`
- `/api/articles/chapter-aux`

機能のAPIやDB表は残す。読者画面からProvider、コンポーネント、初期fetchを外すことで停止する。

## 8. 状態・エラー処理

読者画面は次の5状態を持つ。

1. 標準
2. 空
3. 読込中
4. 部分失敗
5. 全体失敗

全文取得中は本文幅を保ったスケルトンを表示する。全文APIが失敗した場合は、何が起きたか、影響、再試行操作を本文領域へ表示する。

検索や論点索引だけが失敗した場合、本文はそのまま表示し、左パネル内だけにエラーを表示する。補助機能の失敗で法令本文を隠してはならない。

URLの対象Articleが取得した法令内に存在しない場合、近い条文へ推測移動しない。この実装単位ではNot Foundを表示し、正式な墓標ページは恒久URL対応時に追加する。

## 9. 性能要件

性能受入基準は本番ビルドで計測する。

1. 全文読込後、同一法令内の任意アンカー移動は追加通信0件
2. 全文読込後、目次から対象条文が表示位置へ入るまで100ms以内
3. 通常スクロール中に `/api/articles/chapter-window` を呼ばない
4. 建築基準法、建築基準法施行令、建築基準法施行規則で全文表示を検証
5. 最大規模の労働安全衛生規則で、ブラウザが応答不能にならず全文移動できる
6. 全文API応答は本番環境で圧縮される
7. 本文表示に不要な利用者向けAPI通信が0件

100ms基準はデータ取得後のローカルDOM移動に適用する。初回のネットワーク速度は利用環境に左右されるため、別途API応答時間と圧縮サイズを計測・記録する。

## 10. テスト戦略

### 10.1 単体テスト

- flatなDB行から文書ツリーを復元できる
- 条・項・号の文書順を維持する
- Article ID / stableNodeKey から安全な固定アンカーを生成する
- URL対象Articleを正しく特定する
- 不明な対象を近似解決しない

### 10.2 統合テスト

- 全文APIが指定版の1法令だけを返す
- 現行法令集の収録範囲外とsoft delete済みノードを返さない
- 目次と本文の対象Articleが一致する
- ETagとCache-Controlを返す
- 最大規模法令を欠落なく返す

### 10.3 ブラウザテスト

- 建築基準法の冒頭URLと遠方条文URLを直接開ける
- 第2条から第107条へ目次移動しても追加通信がない
- 現在条に合わせて目次選択が更新される
- 検索結果が新しいタブで開く
- 右パネル、適用時点バー、履歴、確認項目が表示されない
- モバイル幅で左パネルがドロワーになる
- 全文API失敗時に再試行できる

既存Vitest、型検査、本番ビルドも回帰条件とする。

## 11. 移行手順

1. 全文取得の純粋なDB関数とテストを追加
2. 全文APIと統合テストを追加
3. `FullLawViewer` とアンカー移動を追加
4. 左目次を全文Document Contextへ接続
5. 読者画面を2列へ変更し、不要Provider・通信を外す
6. 検索結果を新規タブへ変更
7. E2E性能・通信本数を検証
8. 安定後に未使用コード削除を別タスク化

移行中は `ChapterScrollViewer` と既存APIを残す。全文ビューアの受入基準を満たすまで削除せず、障害時に比較できるようにする。ただし新旧切替用の恒久Feature Flagは追加しない。

- §4.3 ApplicabilityContextの利用者向け適用時点切替
- §19.5の注釈・根拠サポートペイン
- §19.10.3の未施行改正・経過措置NoticeBand
- §19.10.5〜6の保存・注釈操作
- §19.14の権限不足状態

Reference Edge自体は維持するが、未確認候補は内部管理だけに表示する。確認済み参照と未解決参照の新表示は、全文ビューア安定後の独立実装単位とする。
