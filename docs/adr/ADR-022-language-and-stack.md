# ADR-022 — 実装言語と初期スタック

- 日付: 2026-07-29
- ステータス: ACCEPTED（S1 着手までは低コストで撤回可能）
- 対応する未解決事項: 設計書 §16 の O-6

## 決定

**TypeScript / Node 22 を、バックエンドとフロントエンドの共通言語とする。**

初期スタック候補を次のとおりとする。S1 着手時に確定する。

| 領域 | 採用候補 | 理由 |
|---|---|---|
| 実行環境 | Node 22 LTS | 導入済み。長期サポート |
| HTTP | Fastify | 軽量、TypeScript 対応が良い、OpenAPI 生成が容易（設計書 §13.4 の必須要件） |
| DB アクセス | `pg` ＋ Kysely（型安全な SQL ビルダ） | SQL 優先。ORM の抽象に隠さない |
| マイグレーション | 生 SQL（node-pg-migrate 等） | EXCLUDE 制約・RLS・CHECK を素の SQL で書く必要がある |
| フロントエンド | React ＋ Vite ＋ TanStack Query / Router | 設計書 §19.18.4 の stale-while-revalidate 方針に一致 |
| テスト | Vitest | 前後で同一のテストランナー |

## 理由

### 1. フロントエンドが TypeScript 確定であり、言語を1つに寄せられる

設計書 §19 でスクロール型リーダー・注釈レイヤー・サポートペインを含む本格的な Web クライアントを定義しており、フロントエンドは TypeScript になる。バックエンドを別言語にすると、Solo Track（1名）が2つのツールチェーン・2つのテスト環境・2つの依存管理を維持することになる。

さらに、設計書 §19.17 は「バッジ類を必須 props とし、未指定でレンダリングできない型定義にする」ことで `DERIVED_CONSOLIDATED` の表示漏れをコンパイル時に防ぐ設計を採っている。API 応答型をバックエンドと共有できれば、この保証をクライアント境界まで一気通貫で効かせられる。言語を分けるとこの利点を失う。

### 2. Python の優位性が、本プロジェクトでは大きく効かない

日本語処理・パースの領域では通常 Python が有利である。しかし本プロジェクトでは次の理由で差が縮む。

- **形態素解析はアプリ層に置かない。** 設計書 §9.2 は日本語トークナイズを PostgreSQL 拡張（pg_bigm / PGroonga）または OpenSearch + Sudachi に置く方針である。アプリケーションコードに Sudachi を組み込まないため、SudachiPy の優位性は発生しない。
- XML / HTML パースは Node でも十分に成熟している（fast-xml-parser、cheerio）。
- 文字正規化（NFKC、漢数字変換、元号変換）は正規表現とテーブル引きの領域であり、言語差が小さい。

### 3. PDF 抽出だけは Python が有利だが、分離できる

告示の画像 PDF・表組み PDF の抽出（設計書 §8.4）は、`pdfplumber` 等の Python エコシステムが優位である。ただしこれは**取込パイプラインの1ステージ**であり、独立したワーカーとして分離できる。

方針: まず Node の PDF ライブラリで F-3 を試し、抽出品質が不足した場合に限り、PDF 抽出ステージだけを Python の別プロセスとして切り出す。最初から2言語構成にはしない。

## 代替案の評価

| 案 | 利点 | 採らない理由 |
|---|---|---|
| Python バックエンド ＋ TS フロント | PDF・日本語処理のライブラリが強い。型ヒントも実用水準 | Solo Track で2言語の維持コストが割に合わない。§9.2 の方針により最大の利点が効かない |
| Go | 単一バイナリ、性能、並行処理 | このワークロードは I/O 律速であり性能問題は起きにくい。文字列処理の記述量が増える。フロントと言語が分かれる |
| Rust | 性能、型安全性 | 設計書 §13.4 が「習熟コストの高い技術を理念だけで採用しない」と明記している。Solo Track で選ぶ理由がない |

## ORM を採らない理由

設計書 §13.1 のスキーマは、次を DB 層で強制する設計になっている。

- `EXCLUDE USING gist` による有効期間の重複禁止（ADR-013）
- Row Level Security によるテナント境界（§12.3）
- `CHECK (valid_from_status <> 'FIXED' OR valid_from IS NOT NULL)`（C-1 の修正）
- EvidenceSnapshot の UPDATE / DELETE をトリガで禁止（ADR-004、墓標化経路を除く）

これらは一般的な ORM のスキーマ DSL では表現できないか、エスケープハッチ頼みになる。**このプロジェクトの正しさは DB 制約に載せてあるため、DB 制約を第一級に書ける方式を選ぶ。** マイグレーションは生 SQL で書き、クエリは型安全なビルダで書く。

## 影響と撤回コスト

現時点で存在するコードは S0 の spike のみであり、使い捨て前提である（README）。S1 着手前であれば、撤回コストは spike の書き直しに限られる。

S1 でアプリケーション本体の実装を始めた後の変更は現実的でない。**S1 着手時にこの ADR を再確認し、確定させること。**
