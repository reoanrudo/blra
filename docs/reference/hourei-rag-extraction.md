## 1. BLRA が取り込むべきもの

### 1.1 【最重要】表示テキストと原文の座標対応（BLRA に無い解法）

hourei-rag は法令本文を**表示用に変換して**描画する。市販法令集と同じく、漢数字を算用数字へ、単位名称を記号へ、割合を分数へ変換する。

```
原文    十分の七以上とし、幅員四メートル
表示    7/10 以上とし、幅員 4m
```

BLRA の設計書はこの変換を想定していない。しかし OCR で確認したとおり、**紙の法令集の見た目に寄せるならこの変換は必須**である（`hourei-shu-2026-ocr.md` §2.1）。

変換すると重大な問題が起きる。**表示テキストの文字オフセットが原文とずれるため、注釈・ハイライト・引用範囲が原文へ紐づかなくなる。** BLRA §6.1 の `text_quote_selector` は「表示テキスト＝原文」を暗黙に前提しており、この場合に破綻する。

hourei-rag の解法は、全トークンに原文座標を持たせることである。

```ts
export interface LegalDisplayToken {
  sourceStart: number;   // 原文上の開始位置
  sourceEnd: number;     // 原文上の終了位置
  displayText: string;   // 画面に出る文字列
  kind: "plain" | "number" | "unit" | "fraction";
}
```

描画時は plain トークンも含めて全てを span で囲み、DOM に座標を残す。

```tsx
<span data-source-start={token.sourceStart}
      data-source-end={token.sourceEnd}
      data-source-kind={token.kind}>
  {token.displayText}
</span>
```

`kind` の用途が巧妙である。`plain` は表示＝原文なのでオフセットを直接計算でき、`number`/`unit`/`fraction` は変換済みなので**一部を選択しても全体へ拡張する**。「4m」の「4」だけを選択させない、という判断である。

**BLRA への反映**: 設計書 §6.1 と §11.5 に影響する。

- §6.1 に「表示変換を行う場合、Citation Anchor は原文座標で保持し、表示層に座標対応を持たせる」を追加する
- §11.5 の Citation Validator「表示抜粋が Source 本文と文字列一致する」は、**表示テキストではなく原文に対して検証する**旨を明記する（`minpou-excerpt-ocr.md` で指摘した問題と同根）

### 1.2 変換の除外規則が市販法令集と一致している

`legal-display-format.ts` の処理順序は次である。

```
1. 除外判定  区分・等級・号構造・公布番号等は原文維持
2. 分数変換  「十分の七」→「7/10」
3. 単位変換  複合単位を先に、次に単独単位
4. 数量変換  残った漢数字の数量を算用数字化
```

除外規則「区分・等級・号構造・公布番号」は、**OCR した市販法令集の表記方法(1)「第一種、一級といった『区分』、法令中の『号』等を除く」と完全に一致する。** 独立に同じ規則へ到達している。

これは F-6 の欠陥3（「号は漢数字のままとするのが法令の慣行」）に対する実装済みの答えでもある。

### 1.3 建築実務の軸に沿ったハイライト分類

`highlight.css` は汎用の色分けではなく、**建築実務の判断軸**でクラスを切っている。

```
use-district      用途地域
fire-district     防火地域
height-limit      高さ制限
building-use      建築用途
structure-type    構造種別
building-coverage 建蔽率
floor-area-ratio  容積率
```

さらに `highlight-border-multi`（複数軸が重なる条項）、`highlight-dimmed`（該当しない条項を減光）、`annotation-badge--applicable / --review / --reference` の3状態を持つ。

BLRA 設計書 §19.17 の `AnnotationMarker` は出所（個人／案件）と AnchorStatus しか持たない。**判断軸による分類という発想が無い。** 案件条件（用途地域・防火地域等）に応じて条文を減光・強調する機能は、設計書 §10 の Project の使い方として有力である。

### 1.4 参照用に法令集の誌面写真を蓄積している

`docs/research/law-book-reference/` に `table-of-contents/` と `article-spreads/` があり、README に「2段組、点線リーダー、マゼンタの章・節見出し、ランニングヘッダーの参考」と記されている。

**BLRA §19.16 のデザイントークンは机上の提案だったが、hourei-rag は実物を参照して決めている。** `--law-paper: #fffdf8`（紙色）、`--law-accent: #d92f7e`（マゼンタ＝2色刷りの赤）、明朝体本文は、実物照合の産物である。

BLRA §19.16.1 で「本文はゴシック標準、明朝は将来オプション」とした判断は、**実物に寄せるなら誤りである。** 市販法令集の本文は明朝であり、hourei-rag もそうしている。

### 1.5 実装して廃止された設計（貴重な反証）

`globals.css` に次のコメントが残っている。

```
/* 2段組み（column-count: 2）は ADR-023 で廃止。
   1条モード・章スクロールモードともに縦1列（1段組み）で統一。
   画面サイズ・コンテナ幅に依存しない。 */
```

実物の法令集は2段組みである。それを再現しようとして実装し、**廃止した。** BLRA §19.2 の「一画面一主スクロール」と同じ結論に、実装を経て到達している。

机上の設計より強い証拠である。BLRA が同じ試行を繰り返す必要はない。

## 2. BLRA が hourei-rag へ提供できるもの

### 2.1 【最重要】告示の答え

hourei-rag の `requirements.md:50` に次がある。

> 総目次の「告示」5群は編集上の集合見出しであり、個別告示名・告示番号の二次資料を得てから別Entryとして追加する。

**hourei-rag は BLRA の F-3 / F-4 と同じ壁に当たり、保留している。** BLRA はここに実測の答えを持つ。

| 問い | BLRA の実測結果 | 出典 |
|---|---|---|
| 告示は e-Gov にあるか | **無い。** law_type に告示の種別が存在しない | F-1 |
| どこから取るか | 国交省の告示ページ。リンク233本すべて PDF | F-3 |
| PDF は読めるか | **テキストPDF。OCR 不要。** 60件中54件（90%）で告示番号を取得 | F-3 |
| 現行全文はあるか | **無い。** 案文と新旧対照表のみ | F-4 |
| 自製統合できるか | 1つの改正が34件以上の告示に及ぶ。Solo Track では不可能 | F-4 |
| どうするか | 案B（案文＋改正履歴の提示に留める） | ADR-023 |
| 再配布してよいか | **PDL1.0 で自由。** 出典明示・加工明示が条件 | F-8 |

`spikes/src/f3-notification-parser/index.ts` が動く取得・抽出コードである。そのまま移植できる。

### 2.2 コーパスの時間的収録範囲

BLRA F-9 の実測。

```
建築基準法      取得可能な最古の施行日 = 2016-09-01（公布は1950年）
建築基準法施行令                      = 2017-04-01
建築基準法施行規則                    = 2017-04-01
```

hourei-rag は「2026年1月1日時点のe-Gov公式XMLを正本とする」としており、現行版のみを扱っているように見える。過去時点の表示機能を追加する場合、**既存不適格の案件では条文を出せない**という制約に必ず当たる。BLRA §4.6 の `coverage_from` と「収録範囲外」を正規の応答とする設計がそのまま使える。

### 2.3 Citation Resolver の欠陥3件

BLRA F-6 で実データ検証した結果。hourei-rag の `link-renderer.tsx` にも同種の問題がある可能性が高い。

1. **号の枝番の silent truncation**: 「第四号の二」→ `item4` と切り捨てられる。第四号と第四号の二は別規定
2. 略称辞書が不足（「建基法」「都計法」が解決できない）
3. 項を省略した号参照（「第二条第九号」＝ 第2条第1項第9号）の補完。これが無いと施行令の解決率が 71% に落ちる

3 は hourei-rag が既に解決している可能性があるが、1 は要確認である。

### 2.4 DB 制約による時点整合性の担保

BLRA F-7 で PostgreSQL 実機検証した7ケース。特に次の2つは hourei-rag にも効く。

```sql
-- 同一 Provision に有効期間が重複する版を DB が拒否する
EXCLUDE USING gist (provision_id WITH =, daterange(valid_from, valid_to, '[)') WITH &&)
  WHERE (valid_from_status = 'FIXED')

-- 施行日未確定（「政令で定める日から施行する」）を仮日付なしで表現する
CHECK (valid_from_status <> 'FIXED' OR valid_from IS NOT NULL)
```

「現行版が2つ存在する」という最悪の不整合を、アプリのバグに関係なく DB が拒否する。要 `btree_gist`。

## 3. 相互に確認できた事実

hourei-rag は BLRA と同じ規律を独立に持っている。特に次は評価に値する。

**証明していないことを証明したと言わない。** `requirements.md:58` に、附則4,973件を照合済みとしたうえで「この件数は公式XML上の保持件数であり、紙の法令集における各附則の掲載範囲を証明するものではない」と明記している。

**未照合部分を表示しない。** `requirements.md:54` は、「抄」106文書について公式全文を原本保全用に保持しつつ、「紙面の収録Range未照合部分を法令集モードへ公開してはならない」としている。BLRA の `consolidation_state` と `DERIVED_CONSOLIDATED` を Primary Citation にしない制約（§5.3）と同じ思想である。

## 4. 判断が必要なこと

**同じ構想のプロジェクトが2つ並走している。** 一方（hourei-rag）は動く実装と120文書の取込を持ち、他方（BLRA）は設計書 v1.1 と S0 の実測結果を持つ。Solo Track（実装1名）で両方を維持するのは、設計書 §15.8 が警告した「可処分時間の奪い合い」そのものである。

現状を踏まえた率直な評価を述べる。

**実装は hourei-rag に一本化するのが合理的である。** BLRA の設計書 §19 が定義した UI は既に hourei-rag に存在し、ADR も22本ある。BLRA 側で `src/` を新設して S1 を始めるのは、動いているものを作り直すことになる。

**BLRA の価値は設計書と S0 の実測にある。** 告示の入手可能性（F-1/F-3/F-4）、遡及範囲（F-9）、pg_bigm の実測（F-7）、Citation Resolver の欠陥（F-6）、利用条件（F-8）は、hourei-rag が現在持っていない、あるいは保留している論点への答えである。これらを hourei-rag へ供給するのが最も無駄がない。

具体的な進め方の案は次である。

1. BLRA の S0 findings（F-1〜F-9）を hourei-rag の `docs/research/` へ持ち込む
2. 告示対応（案B）を hourei-rag の次スプリントとして起票する。`f3-notification-parser` を移植する
3. BLRA の設計書は「上位の設計正本」として残し、実装は hourei-rag で行う
4. BLRA リポジトリでの S1 着手は行わない

ただしこれは事業判断であり、決めるのは Taguchi さんである。2つを別プロダクトとして育てる意図があるなら、この評価は当たらない。
