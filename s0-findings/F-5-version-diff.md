## 設計書への反映が必要な発見（1件）

### 発見: 別表・様式の canonical_path が版間で追跡できない（要・設計書修正）

隣接版の比較で、本文がまったく同一のまま path だけがずれる事象が出た。

```
appdx2254 → appdx2260
appdx2255 → appdx2261
appdx2256 → appdx2262
appdx2257 → appdx2263
```

原因は、別表・様式（`AppdxTable` / `AppdxStyle` 等）の canonical_path を**出現順の連番**で振っているためである。前方に条項が1つ追加されるだけで、以降の別表の path が全てずれる。

これは spike の実装都合ではなく、設計上の問題である。設計書 §6.1 は canonical_path を「Source 内の一時的な HTML id に依存させない」と定めているが、**連番もまた一時的な識別子である**。

影響は小さくない。別表は法令本文から頻繁に参照される（「別表第一（い）欄（一）項」）。連番で振ると、版をまたいだ引用・保存済み根拠・注釈がすべて壊れる。

**対応案**: 別表のタイトル（`AppdxTableTitle` の「別表第一」等）を正規化して path に使う。

```
appdx2254            ← 不可（連番）
appdx-table-1        ← 「別表第一」から生成
appdx-style-1-2      ← 「様式第一の二」から生成
```

タイトルが取れない、または重複する場合のみ連番へフォールバックし、その旨を記録する。

→ **設計書 §6.1 に「別表・様式の canonical_path はタイトルから生成し、連番に依存しない」を追記すべき。S1 のスキーマ確定前に決める。**

## 設計の妥当性が実データで確認できた点

### §6.2 の Anchor 移行（MAPPED）は実在する事象である

本文が同一のまま canonical_path が変わったものを検出した。長期比較で 16 件。

```
art18/para24/item1  → art18/para38/item1   （項の繰下げ。24項 → 38項）
art55/para3/item1   → art55/para4/item1    （項の繰下げ）
art67-3/para3       → art67/para3          （条番号の変更。67条の3 → 67条）
```

設計書 §6.2 が定める 3 状態（EXACT / MAPPED / REVIEW_REQUIRED）と、§19 の「元の条文が改正されました。位置を確認してください」という表示は、**想定上のリスクではなく実際に起きる事象への対応である**ことが確認できた。

特に `art67-3 → art67` は条番号そのものが変わっている。保存済み根拠を canonical_path だけで追跡すると、この改正で参照先を失う。`content_fingerprint` と `text_quote_selector` による多重化（§6.1）が必要であることの実証になる。

横断テスト T-02（Anchor 安定性: 文言修正 / 項追加 / 項削除 / 条番号繰下げ / 附則追加）は、**実データから直接テストケースを作れる**。S1 でこの版ペアを固定して Fixture 化する。
